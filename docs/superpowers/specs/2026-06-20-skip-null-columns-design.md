# Дизайн: параметр `skip_null_columns`

Дата: 2026-06-20

## Проблема

При вставке `dict` в таблицу dbset автоматически создаёт недостающие колонки,
выводя их тип из значений. Если значение ключа равно `None`, тип неизвестен, и
сейчас колонка всё равно создаётся как `Text` (см. `TypeInference.infer_type`,
`types.py:80`). Иногда это нежелательно: пользователь не хочет, чтобы случайные
`None`-поля порождали колонки неясного типа.

## Решение

Добавить параметр `skip_null_columns: bool = False` в `connect()`.

- `skip_null_columns=False` (дефолт): текущее поведение — `None` для
  несуществующей колонки создаёт `Text`-колонку. Полная обратная совместимость.
- `skip_null_columns=True`: ключ со значением `None`, для которого колонки **ещё
  нет**, молча игнорируется — колонка не создаётся и ключ не попадает в INSERT.

Если колонка **уже существует**, `None` пишется как `NULL` в обоих режимах
(параметр влияет только на автосоздание колонок, не на запись в существующие).

## API

`skip_null_columns: bool = False` добавляется в:

- `Database.connect(...)` (`sync_core.py:83`)
- `AsyncDatabase.connect(...)` (`async_core.py`)

Хранится как `self._skip_null_columns` на `Database`/`AsyncDatabase`,
прокидывается в конструктор `Table`/`AsyncTable` рядом с `ensure_schema`.

## Реализация

### Helper

Один приватный метод на `Table` (и зеркально на `AsyncTable`). Чистая функция
над dict, без I/O — `table` уже загружен вызывающим методом:

```python
def _strip_uncreatable_nulls(self, row, table):
    """Отбросить None-ключи, для которых нет существующей колонки."""
    existing = {c.name for c in table.columns}
    return {k: v for k, v in row.items()
            if v is not None or k in existing}
```

### Точки вставки

Сразу после `get_table(...)`, до `infer_types_from_row(...)`, под условием
`if self._skip_null_columns:`. В `sync_core.py` и зеркально в `async_core.py`:

| Метод                       | Что фильтруем                          |
| --------------------------- | -------------------------------------- |
| `insert`                    | `row`                                  |
| `insert_many`               | каждый `row` (по таблице из `rows[0]`) |
| `update`                    | `row`                                  |
| `upsert`                    | `row` (далее делегирует в insert/update) |
| `update_many`/`upsert_many` | каждый `row`                           |

Фильтрация по PRE-существующим колонкам происходит до вывода типов, поэтому
выкинутый ключ не порождает колонку (`ensure_columns` его не видит) и не попадает
в statement. Если колонка уже была — ключ остаётся, `ensure_columns` для неё
no-op, а в INSERT/UPDATE пишется `NULL`.

## Граничные случаи

- **Новая таблица**: `table.columns` содержит только PK → все `None`-ключи
  отбрасываются. Корректно.
- **`insert_many` с гетерогенными строками**: фильтрация по pre-существующим
  колонкам, консистентно с текущим выводом типов только по `rows[0]`.
- **`upsert`**: `None`-ключ из `keys` без колонки и так отсекается существующей
  логикой `index_keys`/`original_keys`; дополнительно подчищается в
  делегируемых insert/update.

## Тесты (sync + async)

- `skip_null_columns=True`: `None` для новой колонки → колонка не создана, строка
  вставлена без неё.
- `skip_null_columns=True`: `None` для **существующей** колонки → записан `NULL`.
- `skip_null_columns=False` (дефолт): `None` → создана `Text`-колонка (регресс
  текущего поведения).
- `insert_many` и `update` в режиме `True`.

## Совместимость

Дефолт `False` сохраняет текущее поведение полностью. Новый параметр опционален.
